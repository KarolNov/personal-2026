blueprint is how I work on larger, architected changes with agents. It sits between
[wayfinder](https://github.com/mattpocock/skills) and [OpenSpec](https://github.com/Fission-AI/OpenSpec): you bring
the solution, and it grills *that* solution in a few short rounds instead of hunting for alternatives. Then it writes
the change up where your team already keeps docs, builds it task by task, and keeps the specs and the code in sync. It lives in my [skills repo](https://github.com/KarolNov/skills) with the other Claude Code skills I
use daily.

## How it works

- **`/blueprint-setup`** looks at where you already track projects and tickets, picks where specs and blueprints live,
  and maps the repo's capabilities to code.
- **`/blueprint <your solution>`** plays it back, sketches it, grills it, and writes a blueprint as two linked
  documents: a plain-text **brief** for agents (decisions, spec delta, tasks) and a visual **review** for people.
- **`/blueprint apply`** builds it task by task, checks each requirement against the code, then folds the change into
  the capability specs.
- **`/blueprint-drift`** and **`/blueprint-sync`** catch the two ways specs and code drift apart: the code strayed from
  the spec, or the spec fell behind the code.
- **`/blueprint coverage`** traces each spec scenario to the tests that claim it. A test claims a scenario with a
  one-line `@scenario` comment, so the report shows which scenarios have unit or end-to-end tests, which have none,
  and which tags point at nothing. Nothing is run: a scenario is claimed, never "passing".
- **`/blueprint-tidy`** groups capabilities into domains, each with an overview page, and moves older setups to the
  current format. It shows one table of moves and writes nothing until you say yes.

A blueprint can also list **artifacts**: things outside the repo that describe a capability, like a Figma file, a
dashboard or a doc. When the code they describe changes, they're flagged as possibly out of date.

## Views

Most of blueprint runs in chat, but a few things are easier to look at than to read about.

**A pane in Claude Code** (`/blueprint-ui`), in the desktop app and the terminal. It opens on a board: which
capabilities need a drift check or a sync and which changes are open, each with a ▶ button for the next step.
Reviews, briefs and specs open in the same pane, read from wherever they live. Comment on a line or suggest a change,
and the batch goes back to `/blueprint` to fold into the next revision.

**The PR plan.** When `/blueprint apply` splits a change into pull requests, the pane draws them as a tree: stacked
on each other, cut from main, or waiting for another group to merge first, with specs last. Once you approve it, ▶ starts each group in its own session.

**The capability map** (`/blueprint map`) isn't part of the pane: it's one local HTML page, drawn from the repo
alone. Capabilities sharing files are tied together. Drifted ones are red, and ones that might be affected are a lighter
red. Clicking one lists its requirements, the tests that claim each scenario, its files and its artifacts. Search
covers all of it.

## Reviews

Every review opens with a before → after diagram with the change coloured in. When a change is about how something
behaves over time, the review can also include a **playground**: a small interactive model that runs the same scenario
through the old and the new design.

Specs and blueprints can live in Notion (the default), Obsidian, Linear, Jira and Confluence, GitHub or a Markdown
folder, with tickets wherever the team keeps them. The only thing in the repo is a small `.blueprint/` folder that
maps capabilities to code and lets `drift.py` tell from git alone which specs need another look.

`drift.py` also follows imports. If a file that a capability's code imports changes, even a few imports away or in
another package, it gives that capability a **drift chance** from 0 to 1 and a confidence, with the reasons behind
both. A high chance counts as drift. A low one is flagged as "possibly affected", so it's worth a look but doesn't
count as drift. For TypeScript it follows imports symbol by symbol, using the repo's own compiler. A ready-made
GitHub Action runs the check on every pull request and keeps one comment up to date, listing the capabilities that
drifted and the artifacts that may need an update.
